Timeouts — Set Them, Or Hang Forever

What's actually happening

  • On a 5% roll, the server accepts your request and goes silent
  • It doesn't error immediately — it sleeps for two full minutes, then finally replies 408
  • Your HTTP client's default is usually "wait forever" — that's the trap
  • You must set your own timeout, well under two minutes

The fix — HttpRequest.timeout()

HttpRequest request = HttpRequest
    .newBuilder(URI.create(url))
    .timeout(Duration.ofSeconds(10))
    .GET()
    .build();

try {
  var res = client.send(request, BodyHandlers.ofString());
} catch (HttpTimeoutException e) {
  // treat like a retryable failure
}
Pick a number well above your slowest normal response (~3s) and well below the 2-minute hang — 8–10 seconds is comfortable. java.net.http.HttpClient throws HttpTimeoutException the moment it fires — no extra library needed.

Retry Logic & Exponential Backoff

The rule

  • firstnames fails outright ~35% of the time — 500, 503, or 504
  • A dropped timeout also surfaces as a failed request — treat 408 the same way
  • Don't retry instantly — back off, or you make the overload worse
  • Always cap the retry count so a truly dead endpoint doesn't spin forever

The shape

int retries = 0;
while (true) {
  var res = client.send(request, BodyHandlers.ofString());
  if (res.statusCode() < 300) return res;

  if (res.statusCode() >= 500 || res.statusCode() == 408) {
    if (retries >= MAX_RETRIES) throw new IOException();
    long backoff = 1000L * (1L << retries); // 1s, 2s, 4s...
    Thread.sleep(backoff);
    retries++;
    continue;
  }
  throw new IOException("HTTP " + res.statusCode());
}
Bonus pattern: a circuit breaker — stop calling an endpoint that's failed N times in a row, wait, then probe again — is the natural next step once retries are working.

Rate Limits — the Number Moves Under You

What makes this one nasty

  • surnames assigns each client a limit between 20 and 60 req/min
  • There's a 10% chance that limit changes again on any given request
  • Whatever worked a moment ago may not work now
  • Hardcoding "wait 2 seconds between calls" will not save you

The fix — honor the header

if (res.statusCode() == 429) {
  long wait = res.headers()
      .firstValue("Retry-After")
      .map(Long::parseLong)
      .orElse(60L);
  System.out.println("Rate limited, waiting " + wait + "s");
  Thread.sleep(wait * 1000);
  continue; // retry without burning an attempt
}
Don't guess the limit — read it every time. The server tells you exactly how long to wait via Retry-After. Trust that over any number you hardcoded five minutes ago.

Cursor Pagination — 20 Trips, Not One

The loop

String cursor = null;
Map ages = new LinkedHashMap<>();

do {
  String url = cursor == null
      ? BASE_URL + "/people/ages"
      : BASE_URL + "/people/ages?cursor=" + cursor;

  JsonNode root = mapper.readTree(
      fetchWithRetry(url).body());

  for (JsonNode item : root.get("data")) {
    ages.put(item.get("id").asLong(), item.get("age").asInt());
  }

  boolean hasMore = root.get("hasMore").asBoolean();
  cursor = hasMore ? root.get("cursor").asText() : null;
} while (cursor != null);

The numbers

0 Records per page
0 Pages to fetch

Every one of those 20 requests carries the same 5% timeout / 30% slowness risk as everything else. Your retry-and-timeout logic has to wrap each page, not just the outer loop.

Stop condition: loop until hasMore is false — not until you've counted to a number you assumed in advance.
